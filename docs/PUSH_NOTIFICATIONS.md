# Push notifications (Firebase Cloud Messaging)

How School OS sends push to the Android app: school notifications (attendance, fees, homework, announcements, messages, leave, results, approvals, missed calls) and incoming calls. It covers what goes in a push, who receives it, how the server authenticates to Firebase, and how to configure and check production. Call-specific behaviour is in `INCOMING_CALLS.md`. The keyless credential option is in `FCM_KEYLESS.md`.

## How it works

```
feature (fees, leave, messaging, …) ──▶ notifyUsers()  ──▶ Notification rows (Updates screen, unchanged)
                                         │             ──▶ live event to open apps (notification.new)
                                         └────────────▶ pushNotifications() ─┐
calls (ringing / ended)  ──────────────────────────────▶ pushToUsers()  ─────┤
                                                                              ▼
                        recipient's own registered devices in the same school ─▶ Firebase Admin SDK (sendEach)
```

- **One path.** Every feature already creates its in-app notifications through `notifyUsers` (`communications.service.ts`), which decides recipients with each feature's existing rules. Push is attached there, so it reaches exactly those recipients. No feature logic changed.
- **One sender.** `push/fcm-admin.ts` uses the Firebase Admin SDK (`firebase-admin` 13), with one named app for the process. The earlier hand-written FCM HTTP and JWT code was removed.
- **Push never blocks the action.** It runs after the notification is saved. If FCM is down or misconfigured, the fee, message or leave decision still succeeds, and the notification is still in the app.

### Message types

| Type | Priority | Android channel | Shown by | Payload |
|---|---|---|---|---|
| School notification | normal | `school_updates` | Android, while the app is in the background or closed. With the app open, the in-app Updates bell refreshes and nothing is shown twice | `notification` block (title, text, tag, private lock-screen visibility) and data `{type: notification, notificationId, category, link}` |
| Missed call | normal | `missed_calls` (can be muted separately) | Same as above | Same as above, category `call` |
| Incoming call | **high** | `incoming_calls_v1` (app's own) | The app's call notification with Answer and Decline | data only `{type: call.incoming, callId, caller, detail, expiresAt, ai}`, time to live = remaining ring time |
| Call ended | high | — | Removes the call notification | data only `{type: call.ended, callId}` |

- **De-duplication:** each notification is pushed once per process, and its Android `tag` is the notification id. A repeat therefore replaces the notification on the phone and never doubles it. An incoming call uses one notification per call id.
- **Retries:** messages FCM rejects for a transient reason are retried up to 3 times with backoff (0.5 s, 1 s, plus jitter). Permanent errors are never retried.
- **"Accepted" is not "delivered".** FCM accepting a message does not mean the phone showed it. The status page reports acceptance only.

### Content and privacy

- A push goes only to devices the recipient registered, in the recipient's school (`schoolId` + `userId` on every device row). A user of another school never receives it, even if a wrong user id were passed.
- Data never contains session tokens, other people's ids or connection ids.
- `PUSH_NOTIFICATION_CONTENT=full` (default): the push shows the notification's own title and text, which the recipient may already see in the app. Lock-screen visibility is *private*, so on a secure lock screen the text stays hidden until the phone is unlocked.
- `PUSH_NOTIFICATION_CONTENT=minimal`: the push says only the kind of update ("Fees update", "New message"). Amounts, names and marks stay in the app.

## Devices

- The app registers with `PUT /devices/push` after sign-in. It registers again when it returns to the front and when FCM rotates the token.
  - It sends the FCM token and a random installation id (generated by the app, not a hardware id). A new token from the same installation replaces the old one.
  - Any signed-in school user may register (this no longer needs the calls plan). A push carries only that user's own notifications, and every call is still authorized per call.
- Sign-out calls `DELETE /devices/push` before the session is revoked. When another account signs in on the same phone, the token moves to that account.
- Tokens FCM reports as unregistered or invalid are deleted at once.
  - Tokens from another Firebase project (for example after the project was changed) are deleted when the same send proves the configured project works.
  - If *every* token fails that way, the server's own project is wrong. Nothing is deleted, and an error is logged instead.
- Devices not seen for 90 days get no notifications. For calls, 30 days counts as reachable.

## Server configuration

| Variable | Example | Meaning |
|---|---|---|
| `FCM_PROJECT_ID` | `school-management-softwa-c42b4` | Firebase project id. Must be the project of the app's `google-services.json`. Optional with a key file (taken from the key), but if set it must match |
| `FCM_SERVICE_ACCOUNT_FILE` | `/etc/school-os/fcm-service-account.json` | **Path** to the Firebase Admin SDK service-account key. Never the contents |
| `FCM_CREDENTIALS` | empty, `service_account_file` or `adc` | `adc` = keyless Workload Identity Federation (`FCM_KEYLESS.md`) |
| `GOOGLE_APPLICATION_CREDENTIALS` | | `adc` only: the external-account configuration (holds no secret) |
| `FCM_DRY_RUN` | `false` | `true` on staging: FCM validates every message and delivers none |
| `PUSH_NOTIFICATION_CONTENT` | `full` | `full` or `minimal` (above) |

At start-up the server validates the configuration and **refuses to start** with a message saying what to fix when:
- the key file is missing, unreadable or not JSON;
- the file is not a service-account key (for example `google-services.json` by mistake);
- `project_id`, `client_email` or the private key is missing or malformed;
- the key's project differs from `FCM_PROJECT_ID`;
- the settings are half done (a project without credentials, or `adc` without a project).

Messages never include the key's contents. When configured, the start-up log names the project and credential mode. In production, push being off is logged as a warning.

**Environments:** use a separate Firebase project (or at least `FCM_DRY_RUN=true`) for staging. Device tokens are stored per database, so a development database never holds production phones. Automated tests replace the sender and never contact Google.

## Checking it

| Command / page | What it shows |
|---|---|
| `npm run push:check` | Credential mode, project, service-account email (not the key); the key file is valid and matches `FCM_PROJECT_ID` |
| `npm run push:check -- --google` | Also asks FCM to validate a message to a token that cannot exist (dry run). Proves Google accepts the credentials for this project. Nothing is delivered |
| Platform admin › `GET /platform/integrations` → `push` | Configured or not, project, credential mode, dry run, configuration error, registered devices, and counts since start: accepted, invalid tokens removed, failed, last success or failure, last error code. No keys or tokens |
| Logs | `Push refused by FCM` (credential or project problem, at most once a minute); `Some push messages were not accepted by FCM` (counts only). Never tokens, keys or message text |

## Production checklist

1. **Firebase project.** In the Firebase console (project `school-management-softwa-c42b4`, or your production project), check that the Android app `com.schoolosmobile` exists and that the Cloud Messaging API (V1) is enabled.
2. **App configuration.** Put that project's `google-services.json` at `SchoolOSMobile/android/app/google-services.json`. Check that `project_info.project_id` equals `FCM_PROJECT_ID`, and `client[].client_info.android_client_info.package_name` is `com.schoolosmobile`. Build the release APK or AAB. The Google services plugin and `firebase-messaging` are included only when the file exists.
3. **Server key.**
   - In *Project settings › Service accounts › Generate new private key*, download the key.
   - Copy it to the server outside the repository, for example `/etc/school-os/fcm-service-account.json`.
   - Make it readable only by the API's user: `chown schoolos: …; chmod 600 …`.
   - Do not commit it, email it or paste it into chat. `.gitignore` excludes `*service-account*.json` and `*firebase-adminsdk*.json`.
4. **Environment.** Set `FCM_PROJECT_ID` and `FCM_SERVICE_ACCOUNT_FILE` in the production `.env`. Leave `FCM_DRY_RUN=false` and choose `PUSH_NOTIFICATION_CONTENT`.
5. **Validate before restarting.** On the server, run `npm run push:check -- --google`. It should print `Google accepted the credentials for project …`.
6. **Restart the API.** The log should show `Push notifications on: project …, credentials service_account_file`. If the configuration is wrong, the API does not start and says why. Fix it, or roll back as in step 9.
7. **Index.** The new `installationId` index on `pushdevices` is created by `npm run db:indexes -- --apply`. It is also synced automatically outside production.
8. **End-to-end check with your own phone and a test account:**
   - Install the new build and sign in. Allow notifications.
   - Put the app in the background, and have a test teacher send the test parent a message.
   - A notification should appear. Tapping it should open the conversation.
   - Check `/platform/integrations`: `accepted` should go up and `failed` should stay 0.
   - With calls in the plan: lock the phone for 5 minutes, call it, and check that Answer and Decline work.
9. **Rollback.** Remove `FCM_SERVICE_ACCOUNT_FILE` and `FCM_PROJECT_ID` (or the whole block) and restart. Push is then off. Everything else, including in-app notifications and calls while the app is open, works as before. To revoke a leaked key, delete it under *Service accounts* in Google Cloud and generate a new one.
10. **Monitoring.** Watch for `Push refused by FCM` in the logs and for `failed` or `lastErrorCode` in `/platform/integrations`. A rising `invalidDevicesRemoved` is normal (uninstalls).

## Limits (Android and FCM)

- Delivery is best effort.
  - A **force-stopped** app receives nothing until the user opens it again.
  - Battery savers on some phones (Xiaomi, Oppo, Vivo, Huawei, …) delay or drop push unless the app is allowed to run in the background.
  - Notifications need the notification permission (Android 13+). Without the full-screen permission (Android 14+), an incoming call shows as a heads-up notification.
- High priority is used only for calls, as FCM requires: messages that need immediate user attention. Normal school notifications may be delayed while the phone is idle (Doze).
- There is no iOS app; push is Android only.
